## 1. 前提

B2B受発注システム。企業ごとに複数ユーザーが存在。注文を作成・閲覧・取消できる。企業内管理者は追加権限を持ち得る。発送準備開始後の取消は禁止。取消によって在庫引当解除が必要。

API: `POST /orders/{orderId}:cancel`。入力は注文ID、信頼された実行主体コンテキスト、必要なリクエスト識別子。利用者が主体・テナントを任意に申告した値を信用しない。

対象ドメイン: `Tenant`, `User`, `Order`, `Inventory`。`CancelOrder`ユースケース、`Order`集約の状態遷移、在庫引当解除の外部境界を区別する。

## 2. 保護対象・セキュリティ要求

| ID | 要求 |
|---|---|
| SR-01 | 信頼できる主体のみ取消操作を実行できる |
| SR-02 | 他テナントの注文にアクセスできない |
| SR-03 | 権限ある利用者のみ対象注文を取り消せる |
| SR-04 | 取消禁止状態から遷移できない |
| SR-05 | 取消と引当解除の整合性を保つ |
| SR-06 | 大量取消要求による資源枯渇を抑制する |
| SR-07 | 誰が何をいつ実行したか追跡できる |
| SR-08 | リトライ・重複で二重副作用が起こらない |

SR-04/05は業務・整合性要件でもある。攻撃者による悪用を考慮するとセキュリティ要求として追跡できる。

## 3. 脅威モデル

| ID | 脅威 | 関連要求 |
|---|---|---|
| T01 | 他人の注文IDによる不正取消（BOLA） | SR-02/03 |
| T02 | 一般利用者による管理者専用操作（BFLA） | SR-03 |
| T03 | 漏洩トークンによる操作 | SR-01 |
| T04 | 取消不能状態の注文取消 | SR-04 |
| T05 | 発送開始と取消が競合 | SR-04/05 |
| T06 | 重複要求・再配信による二重処理 | SR-05/08 |
| T07 | 大量取消による資源濫用 | SR-06 |
| T08 | 監査イベント不足で追跡不能 | SR-07 |
| T09 | 注文ID列挙による存在・所属推測 | SR-02/03 |

**注意**: T08は攻撃行為そのものというより検知・調査能力の欠損。実運用のリスク評価には可能性・影響・既存対策の根拠が必要であり、ここではスコアを創作しない。

## 5. 責務配置と実行モデル

| 境界 | 責務 |
|---|---|
| Gateway | TLS、入口レート制限、認証情報検査 |
| Presentation | 形式・スキーマ検証、入力変換 |
| Application Service | 対象取得、認可、ユースケース調整、冪等性キー取り扱い |
| Order Aggregate | 取消可能性、不変条件、状態遷移 |
| Repository | 永続化、トランザクション、競合検出 |
| Outbox | 状態更新と同一トランザクションでイベント記録 |
| Inventory | 冪等な引当解除、再試行・照合 |
| Audit | 重要な成功・拒否・失敗の安全な記録 |

想定フロー: 認証→入力検証→対象注文の認可→状態検証→排他を伴う状態更新＋Outbox書込み→コミット→イベント配信→冪等な在庫引当解除。適切なトランザクション境界・機密情報の扱い・監査の順序は詳細設計で決める。非同期処理では結果整合性となり、在庫更新が即時完了するわけではない。

### 認可と不変条件の違い

- `mayCancel(actor, order)` は主体・テナント・対象・操作の認可判断。
- `canCancel(order)` は注文の現在状態に関する業務判断。
- 操作時点の権限を再評価する。状態検証と永続化間の競合を対処する。

## 6. セキュリティテスト案

| ID | 条件 | 期待結果 |
|---|---|---|
| ST-01 | 認証情報なし | 拒否 |
| ST-02 | 他テナント注文 | 拒否、存在情報を不必要に漏らさない |
| ST-03 | 他人の注文 | ポリシーに従い拒否 |
| ST-04 | 管理者専用機能を一般利用者が実行 | 拒否 |
| ST-05 | 発送準備済み注文 | 状態変更なし |
| ST-06 | 発送開始と取消の並行実行 | 競合を検出し一貫した結果 |
| ST-07 | 同一要求の再送 | 二重副作用なし |
| ST-08 | Outboxイベント再配信 | 二重の引当解除なし |
| ST-09 | 処理途中の障害 | 部分更新・イベント喪失の防止 |
| ST-10 | 大量要求 | 流量・資源制限に従う |
| ST-11 | 成功/拒否の実行 | 必要な監査証跡を記録 |
| ST-12 | 失効権限 | 新たな認可判定で拒否 |

このテスト表は計画であり、テスト実行・成功を示す証拠ではない。SR-01〜08、T01〜09、パターン、検証条件の完全な追跡はIRで定義する。

## 7. 設計体系へのフィードバック

1. セキュリティ専用パターンと、セキュリティに寄与する一般的な分散システムパターンを区別する。
2. ポリシー所有・判定点・強制点を分ける。
3. Verification（確認活動）とAssurance（根拠をもつ主張）を分ける。
4. PatternRelationshipだけでなくPatternComposition（順序、障害時の振る舞い、トランザクション境界）を導入する。
