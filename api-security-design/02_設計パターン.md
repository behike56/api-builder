# セキュリティ設計パターンの体系

[目次へ](README.md) · [基本体系](01_基本体系.md) · [ケーススタディ](03_ケーススタディ_注文キャンセルAPI.md) · [Security Design IR](04_Security_Design_IR.md)

更新日: 2026-10-30 / 状態: 候補カタログ v0.1（名称の一部は本検討での仮称）

## 1. 定義と同定基準

**設計パターン**: 繰り返し発生するセキュリティ設計問題について、特定の文脈・制約の下で原則を具体化し、制御を成立させる再利用可能な設計解。

同定条件: **反復性、文脈依存性、構造性（責務・相互作用・状態遷移）、再利用性、トレードオフ**。TLSやJWTの採用それ自体はパターンとは限らない。

パターン記述テンプレート: `Context`, `Problem`, `Forces`, `Principle`, `Solution`, `Structure`, `Controls`, `Consequences`, `Verification`, `RelatedPatterns`。

## 2. 7群・21候補

| 群 | ID | パターン候補 | 解決する問題 |
|---|---|---|---|
| P1 主体・権限 | P1-01 | Centralized Identity Provider | ID管理の分散 |
| | P1-02 | PEP/PDP Separation | 認可判断と強制の責務混在 |
| | P1-03 | Resource-Level Authorization | 対象ごとの認可漏れ |
| P2 信頼境界 | P2-01 | Authenticated Service Boundary | サービス間の暗黙的信頼 |
| | P2-02 | Network Segmentation | 侵害拡大 |
| | P2-03 | Controlled Outbound Access | SSRFや外向き通信濫用 |
| P3 契約・データ | P3-01 | Strict Schema Contract | 曖昧な入力契約 |
| | P3-02 | Allowlisted Field Mutation | 不正フィールド更新 |
| | P3-03 | Explicit Response Projection | 過剰な出力 |
| P4 ドメイン・業務 | P4-01 | Domain Primitive | 不正値の生成 |
| | P4-02 | Explicit State Transition | 不正な状態遷移 |
| | P4-03 | Protected Business Workflow | 正規APIによる業務悪用 |
| P5 資源・耐障害 | P5-01 | Rate Limiting & Quotas | リクエスト濫用 |
| | P5-02 | Bounded Resource Consumption | 無制限の資源利用 |
| | P5-03 | Timeout & Circuit Breaker | 障害の伝播 |
| P6 検知・対応 | P6-01 | Security Audit Trail | 追跡不能 |
| | P6-02 | Security Event Detection | 発見遅延 |
| | P6-03 | Credential Revocation | 漏洩後の継続アクセス |
| P7 保証 | P7-01 | Threat-Driven Security Test | 脅威とテストの乖離 |
| | P7-02 | Contract Security Testing | 契約と実装の不整合 |
| | P7-03 | Authorization Matrix Testing | 権限組合せの抜け |

P1〜P6は主としてランタイム保護、P7は開発・保証の活動パターン。P5-01など制御名に近い候補は「分散レート制限」「階層的クォータ」等の構造へ精緻化すべき。P6-01も証跡の完全性・保持・アクセス制御を含めて詳細化する。

## 3. 関係モデル6種

| 種類 | 意味 | 例 |
|---|---|---|
| `Requires` | 成立する前提能力が必要 | リソース認可には信頼できる主体識別 |
| `Complements` | 保護を補完 | 認可と監査 |
| `Alternative` | 同じ問題への異なる設計解 | 中央PDPとローカルPDP |
| `Conflicts` | 両立に制約・トレードオフ | 高鮮度の権限判定と長期オフライン評価 |
| `Refines` | 抽象解を具体化 | 認可→オブジェクト単位認可 |
| `Mitigates` | 他のパターンの副作用を緩和 | キャッシュのTTL・失効 |

関係に成立条件、影響する品質属性、根拠、版を付与する。`Requires`は特定パターンの強制ではなく必要能力の条件である場合がある。

## 4. 選択プロセス

`Context → SecurityRequirement → Threat/Risk → ControlSelection → PatternComposition → Evaluation`。

1. **必須条件による足切り**: セキュリティ要求、規制、前提能力、信頼境界、実現可能性を満たすか。
2. **トレードオフ比較**: Security Coverage、Architectural Fit、Operational Complexity、Performance Impact、Verifiability、Evolvability。

必須の保護を満たさない案を性能・容易性の高得点で相殺しない。採用しない代替案もADRで記録。

## 5. 代表的パターン

### P1-02 PEP/PDP Separation

- Context: 複数APIが共通認可ポリシーを必要とする。
- Problem: 認可実装が各ハンドラーに分散すると漏れ・重複が発生する。
- Solution: 判断点PDPと強制点PEPを分離し、主体・対象・操作・環境を評価。
- Forces: 一貫性と自律性、遅延・可用性・キャッシュ鮮度。
- Verification: 権限変更、他者リソース、PDP障害、拒否時の安全性。

### P3-02 Allowlisted Field Mutation

- Context: リソース更新API。
- Problem: マスアサインメントによりサーバー管理項目が上書きされる。
- Solution: 更新可能項目の明示、DTOでの選別、必要なフィールド単位認可。
- 注意: フィールドマスクそのものは認可機構ではない。

### P4-02 Explicit State Transition

- Context: 注文・申請・決済など状態を持つドメイン。
- Problem: `status` の任意更新が業務不変条件を破る。
- Solution: `cancelOrder` のような意味的な操作と許可状態遷移をモデル化。
- Verification: 取消不可、重複、競合、権限失効。

## 6. 適用・合成と補助パターン

注文取消は、主体識別、対象リソース認可、厳格なAPI契約、状態遷移、監査、脅威に基づくテストの合成となる。

ケーススタディから追加候補:

- **Idempotent Command Processing** — リトライ/重複による副作用の重複を防ぐ。
- **Transactional Outbox** — DB更新とイベント記録を同じトランザクションに載せる。
- **Optimistic Concurrency Control** — 状態検証と更新の競合を検出する。

これらはセキュリティ専用ではないが、業務の完全性を保護する。Outboxのみで外部サービスへの正確に1回の配信は保証されない。消費側の冪等性・再試行・照合も必要。
