# APIセキュリティ設計 — 基本体系

## 1. 設計の目的

APIが提供する業務価値、情報資産、操作・処理の正当性を保護する。認証技術を列挙することと、セキュリティ設計を体系化することを区別する。

## 2. 8つの基本整理軸（本検討の提案）

| 軸 | 問い | 対象 |
|---|---|---|
| 1 保護対象 | 何を守るか | 資産、データ、機能、業務フロー |
| 2 脅威・リスク | 何から守るか | 攻撃者、経路、脆弱性、影響 |
| 3 セキュリティ原則 | どの規範で判断するか | 最小権限、デフォルト拒否等 |
| 4 セキュリティ制御 | どう防止・検知・対応するか | 認証、認可、検証、暗号等 |
| 5 設計・実装境界 | どこに責務を置くか | Gateway、API、Application、Domain、Infrastructure |
| 6 信頼・データフロー | どの境界を越えるか | 主体、通信、外部API、保存 |
| 7 検証・保証 | どう正しさを確認するか | 脅威モデル、テスト、証拠 |
| 8 運用・改善 | どう維持するか | 監視、脆弱性管理、対応、変更管理 |

横断軸: ライフサイクル（要件→設計→実装→検証→運用）、品質特性（機密性・完全性・可用性・真正性・監査可能性）、責任分担。

## 3. 概念の区別

`Asset / Threat → SecurityRequirement → Principle → DesignDecision → SecurityControl → PatternApplication → Implementation → Verification / Assurance`

これは必ずしも直線ではなく、多対多の関係を持つ概念グラフである。

- **要求**: 何を満たすか（例: 他人の注文を取消できない）。
- **原則**: 判断規範（例: 最小権限）。
- **制御**: 保護機能（例: オブジェクト単位認可）。
- **パターン**: 文脈と制約の下で再利用できる設計解（例: PEP/PDP分離）。
- **実装技術**: プロトコル・ライブラリ・コード等（例: OAuth 2.0、OIDC、JWT、OPA）。
- **保証**: 特定の安全性主張と、それを支える評価・証拠。設計済みであることと検証済みであることを混同しない。

OAuth 2.0・JWTの採用だけでは個別リソースへの認可は保証されない。

## 4. 原則の5群（本検討の提案）

| 群 | 主な原則 | 判断の焦点 |
|---|---|---|
| 信頼・アクセス | 最小権限、完全仲介、デフォルト拒否、ゼロトラスト | 誰が何をできるか |
| 境界・分離 | 最小公開、責務分離、最小共通機構 | 攻撃面・波及範囲 |
| 安全な振る舞い | フェイルセキュア、安全な初期値、不変条件保護 | 異常時・状態の安全性 |
| 多層的保護 | 多層防御、侵害前提 | 単一制御の失敗への耐性 |
| 継続的保証 | セキュア・バイ・デザイン、継続的検証、監査可能性 | 開発から運用まで |

ゼロトラストは単一技術ではなく信頼の扱い方、セキュア・バイ・デザインは開発横断のアプローチである。

## 5. セキュリティ制御の4分類軸

- **A 制御機能**: 何を制御するか。
- **B 制御目的**: 予防・検知・対応・復旧。
- **C 保護対象の粒度**: 主体、操作、オブジェクト、プロパティ、業務フロー、データ・資源。
- **D 適用境界**: Gateway、API、Application、Domain、Infrastructure。

制御は複数軸の属性を持ち、複数の原則に同時に対応し得る。

### 制御機能9領域

| ID | 領域 | 代表例 |
|---|---|---|
| C01 | 識別・認証 | ID確認、トークン検証、サービス認証 |
| C02 | 認可・アクセス制御 | RBAC、ABAC、BOLA/BOPLA/BFLA対策 |
| C03 | 入出力・データ境界保護 | スキーマ、型、出力制限、注入防御 |
| C04 | データ・秘密情報保護 | 暗号化、署名、鍵・秘密情報管理 |
| C05 | 業務ロジック・状態保護 | 不変条件、状態遷移、業務制約 |
| C06 | 資源・可用性保護 | レート制限、クォータ、タイムアウト |
| C07 | 通信・実行環境保護 | TLS、ネットワーク分離、SSRF対策 |
| C08 | 監視・監査・検知 | イベントログ、トレース、異常検知 |
| C09 | 運用・インシデント対応 | 資格情報失効、遮断、復旧 |

### 責務配置例

| 境界 | 典型的な責務 |
|---|---|
| Gateway | TLS、入口の流量制御、認証検証 |
| API/Presentation | 契約・入力・出力の境界 |
| Application | ユースケース認可、対象リソース認可、処理調整 |
| Domain | 業務上の正当性、不変条件、状態遷移 |
| Infrastructure | DB権限、暗号、外部接続、永続化 |

認証済み≠操作認可済み。`canCancel(order)`の業務可否と、`mayCancel(actor,order)`の認可を区別する。認可は現在の権限・所有関係の鮮度を考慮する。

## 6. 制御仕様の推奨項目

`controlId`, `requirementRefs`, `threatRefs`, `principleRefs`, `function`, `purpose`, `protectedTarget`, `enforcementPoint`, `decisionOwner`, `patternRefs`, `verificationRefs`, `evidenceRefs`。

## 7. 現時点の境界と課題

制御・パターン・技術・保証活動の分類を混ぜない。制御をどこで強制するかと、ポリシーを誰が定義・判断するかを分離する。セキュリティ専用パターンだけでなく完全性を守る一般的な分散システムパターンも必要。詳細は[設計パターン](02_設計パターン.md)と[Security Design IR](04_Security_Design_IR.md)。
